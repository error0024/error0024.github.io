Anthropic just dropped VP ≠ VNP.

([the repo](https://github.com/anthropics/formal-math/tree/main/vp-vnp))

If this is the first time you're hearing about VP and VNP, same here. The letters look like P and NP, and one of the most relevant Millennium Prize Problem for cryptography, so I decided to take a slightly closer look. 

The short version
======

VP and VNP are the algebraic analogues of P and NP. They're about **families of polynomials**, not languages, and complexity is measured by the **number of gates** (additions and multiplications) in an arithmetic circuit.

- **VP** ("easy to compute"). A family (f_n) is in VP if the number of variables and the degree of f_n are polynomial in n, and f_n is computed by an arithmetic circuit of polynomial size.
- **VNP** ("explicitly defined"). A family (f_n) is in VNP if it can be written as an exponential sum
  f_n(x) = Σ_{e∈{0,1}^m} g_n(x, e), where g_n ∈ VP and m = poly(n).

Each term is easy to compute, but there are exponentially many terms. The question is whether you can add them all up fast.

The claim: a VNP-complete family can't be compressed like that. You need more than polynomially many gates.

Let's look at an example.

Determinant vs. permanent
======

Take a 2×2 matrix:

```
| a  b |
| c  d |
```

- determinant: det = a·d − b·c
- permanent: per = a·d + b·c

Same thing, just with a plus. For the matrix with 1, 2, 3, 4: det = 4 − 6 = **−2**, per = 4 + 6 = **10**.

For n×n it's the same idea. Pick one entry from each row, all in different columns (that's a permutation), multiply them, and sum over all n! permutations. The determinant attaches a sign to each term (the parity of the permutation). The permanent uses all pluses.

For 3×3 there are 6 terms:

```
| a  b  c |
| d  e  f |
| g  h  i |
```

| Columns | Term | det | per |
|---|---|---|---|
| 1,2,3 | a·e·i | + | + |
| 1,3,2 | a·f·h | − | + |
| 2,1,3 | b·d·i | − | + |
| 2,3,1 | b·f·g | + | + |
| 3,1,2 | c·d·h | + | + |
| 3,2,1 | c·e·g | − | + |

With the numbers 1…9:

```
| 1  2  3 |
| 4  5  6 |
| 7  8  9 |
```

The terms are 45, 48, 72, 84, 96, 105. So det = 45 − 48 − 72 + 84 + 96 − 105 = **0**, while per = sum of all = **450**.

For 100×100 that's 100! ≈ 10¹⁵⁸ terms. Nobody computes either one this way.

### Why the determinant is easy

For the determinant computation you can apply Gaussian elimination. Adding a multiple of one row to another doesn't change the determinant. So you just zero out everything below the diagonal:

```
| 2  1  1 |      | 2  1  1 |      | 2  1  1 |
| 4  3  3 |  →   | 0  1  1 |  →   | 0  1  1 |
| 2  2  3 |      | 0  1  2 |      | 0  0  1 |
```

(R2 − 2·R1, R3 − R1, then R3 − R2.)

Now it becomes triangular, so det = product of the diagonal = 2·1·1 = **2**. That's about n³ operations instead of n!, and there are division-free versions (Berkowitz 1984). So **det ∈ VP**.

The minus signs are crucial for this to work, because some of the terms cancel, and this way we can find the shortcut.

### Why the permanent isn't (as far as we know)

Same matrix, permanent:

per = 2·(9 + 6) + 1·(12 + 6) + 1·(8 + 6) = 30 + 18 + 14 = **62**

The triangular matrix after elimination has permanent 2·1·1 = **2**.

Row operations now **change** the permanent. Without minus signs there's nothing to cancel, and the shortcut is gone.

The known algorithm (Ryser, 1963) takes about 2ⁿ·n operations. That's much better than n!, but still exponential: around 10³² for a 100×100 matrix.


### One more character: the Hamiltonian cycle polynomial

Over a field where 1 + 1 = 0 (characteristic 2), minus equals plus, so **the permanent is the determinant** and becomes easy. To cover every field you need a polynomial that stays hard: sum the products only over permutations that are a single cycle through all vertices. For 3 vertices:

HC = x₁₂·x₂₃·x₃₁ + x₁₃·x₃₂·x₂₁

This one is VNP-complete over every field.

What exactly is claimed
======

The paper "VP ≠ VNP over every field" claims that any arithmetic circuit for the Hamiltonian cycle polynomial (over any field), or for the permanent (characteristic ≠ 2), needs more than

m^(c·(log m)^(1/3))

gates. That grows faster than every polynomial, so VP ≠ VNP. It also claims the same bound for approximating circuits, so VNP isn't even in the closure of VP.

It comes with a Lean 4 formalization.

**Caveats:**

- The README says no human mathematician has checked the proof yet.
- Lean checks that the formal statement is proved, but not that `Statement.lean` actually defines the standard VP and VNP. So far only another AI has looked at that.

Does this solve P vs NP?
======

It does not, otherwise they would have said they solved P vs NP :).
But let's look what are the problems.

**It's a weaker model.** An arithmetic circuit can only add and multiply. That's it. A Boolean circuit can do anything with bits: compare numbers, branch, take things mod 2. Showing that the weak model can't compute the permanent tells you nothing about the strong one.

The known connection actually runs the other way. Bürgisser (2000) showed: if VP = VNP over a finite field, then NP ⊆ P/poly. (Over ℚ or ℂ the same holds if you also assume the Generalized Riemann Hypothesis — which, as of last week, also has a claimed Lean-checked proof from Anthropic. What a month :).) 


**Polynomials vs. functions.** An arithmetic circuit has to output the exact polynomial, coefficient by coefficient. A Boolean circuit only needs the right answer on the inputs it actually gets, which are 0s and 1s.

And on 0s and 1s, x² = x. As polynomials, x² and x are different. As functions on {0, 1}, they're the same. Or take x² − x: as a polynomial it's not zero, but on {0, 1} it's always 0.

So a Boolean circuit that counts perfect matchings (the permanent of a 0/1 matrix) doesn't have to compute the permanent polynomial at all. It can compute some completely different polynomial that happens to agree on 0/1 matrices. Or it can skip polynomials and juggle the bits of the numbers directly.

The theorem rules out small circuits for the exact polynomial. It says nothing about any of these shortcuts.

Still, if it holds up, it's a 47-year-old conjecture, settled by an AI.
But for cryptographers it says nothing about one-way functions or average-case hardness. Those are Boolean, average-case properties, while this result is algebraic and worst-case. It doesn't make any crypto assumption more or less plausible.
